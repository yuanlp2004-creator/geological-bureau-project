# GeoSpectrum 项目阅读指南

本文是本项目的代码与资料入口，面向第一次接手代码、定位缺陷、核对旧版行为、扩展业务模块和执行发布验收的开发者。

本文描述的是当前工作区的真实状态，不替代 [AGENTS.md](../AGENTS.md) 的执行约束、[PLAN.md](../PLAN.md) 的范围与门禁，也不替代各步骤的验收报告。遇到冲突时，按 `AGENTS.md` 规定的事实来源顺序判断。

需要逐模块理解实现时，进入 [`代码导读/README.md`](代码导读/README.md)。该目录为 18 个正式模块分别提供中文导读，并补充前端、数据库/API 和 Tauri 发布链的跨层说明。

## 1. 先建立正确的项目边界

项目目标是在 [`app/`](../app/) 中以 FastAPI、React/TypeScript、SQLite 和 Tauri 2 重构 SpecDirect 2.0.2。几个容易混淆的目录承担完全不同的职责：

| 路径 | 用途 | 阅读注意事项 |
|---|---|---|
| [`app/`](../app/) | 新版正式实现、测试与构建工具 | 新功能只在这里实现 |
| [`docs/`](./) | 研究、基线、验收与发布文档 | 用来确认“已经验收了什么” |
| [`Spec Source/`](../Spec%20Source/) | 旧 Delphi/VCL 源码和原始协议资料 | 旧业务规则的主要源码证据 |
| [`Spec2.02/`](../Spec2.02/) | 旧版实际运行目录、配置、方法库和现场数据 | 用于复现行为和兼容验证，保持只读 |
| [`SpecFile/`](../SpecFile/) | 旧资料的分类索引与副本 | 先读其中 README 和来源清单，结论仍须回到原件 |
| [`Spec2.02功能研究/`](../Spec2.02功能研究/) | 对旧功能、源码和截图的整理结果 | 适合快速定位，不替代原始证据 |
| `UI测试/`（若资料存在） | 前端视觉样式参考 | 不能从中推断业务、接口、数据或架构 |

可直接启动的便携演示包归档在 [`releases/0.1.0/GeoSpectrum_便携演示版/`](releases/0.1.0/GeoSpectrum_便携演示版/)；其中两个 EXE 是未签名内部测试产物，不是源代码，也不是正式发布通过的证明。正式实现、构建规则和发布证据分别以 `app/`、`app/README.md` 和 `acceptance-reports/` 为准。

5. 读 [`app/README.md`](../app/README.md)，了解环境、运行、构建和发布命令。

   - [`app/backend/api/system.py`](../app/backend/api/system.py)：已拆出的系统接口

这个顺序先回答“有哪些模块”，再回答“如何装配、如何存储、前端如何调用、桌面壳如何启动”。

### 3.2 定位一个业务功能

按以下链路向下追踪：

```text
模块清单 manifest.py
  → 前端入口 navigation.ts / App.tsx 或独立页面组件
  → 前端契约与请求 api/<business>.ts
  → FastAPI 路由 api/<module>.py
  → 业务服务 backend/modules/<module>.py
  → SQLite 网关 db.py → 表与历史迁移 migrations/
  → tests/ 中同名或同步骤测试
  → docs/acceptance-reports/Sxx/验收报告.md
```

如果先拿到的是 API 路径，可在 `backend/api/` 搜索路径；如果先拿到的是表名，可在 `migrations/` 和 `modules/` 中同时搜索；如果先拿到的是界面文字，可先在 `frontend/src/` 搜索，再反查调用的 `api.*` 方法。

## 4. 运行时架构

桌面模式的主链路如下：

```text
Tauri 主进程 main.rs
  ├─ 选择仅绑定 127.0.0.1 的随机端口
  ├─ 生成一次性进程密钥
  ├─ 启动 geospectrum-backend sidecar
  └─ 通过 sidecar 标准输入传递密钥
             ↓
backend/sidecar_entry.py
  ├─ 确定运行数据目录
  ├─ 迁移旧数据目录（只复制并校验）
  ├─ 在副本中执行数据库升级
  └─ 启动 backend.main:app
             ↓
FastAPI main.py
  ├─ 进程密钥中间件
  ├─ Bearer 会话与权限依赖
  ├─ Pydantic 请求/响应契约
  ├─ 模块应用服务
  └─ Database → SQLite/WAL

React 前端
  ├─ 通过 Tauri runtime_config 取得 api_base 与进程密钥
  ├─ api/client.ts 发出 HTTP 请求，api/events.ts 生成 WebSocket 地址
  ├─ /api/v1/capabilities 返回模块及导航契约
  └─ navigation.ts 按权限和当前方法状态生成可用入口
```

浏览器开发模式没有 Tauri 的 `runtime_config`，`api/client.ts` 使用同源相对路径，文件保存退回浏览器下载。桌面模式的前端文件保存统一调用 Tauri `save_export_file`，由 Rust 校验叶子文件名、扩展名、内容类型、内容头和大小后再打开“另存为”对话框。

## 5. 三个集中装配点

当前代码已经按业务服务拆分，但还不是每个模块都拥有独立的 `domain/application/repository/api` 目录。R3 已把后端 API 和模型按业务拆分，main.py 只保留应用装配；db.py 仍承载数据库基线与迁移；前端 App.tsx 已缩为认证入口，WorkspaceApp 负责跨页面装配：

### 5.1 `backend/main.py`：HTTP 组合根

- 创建 FastAPI 应用和生命周期。
- 装配数据库、通用服务、认证服务和各业务服务。
- 注册 `api/middleware.py` 中的 Pydantic 校验错误转换与进程密钥/CORS 中间件。
- 调用 `api.register_api()` 注册各业务 REST 路由及 `api/events.py` 的 WebSocket。
- 具体路由在 `api/<module>.py` 执行权限检查，把输入交给模块服务。

新增业务规则不应直接堆进路由；路由负责鉴权、协议转换和错误映射，规则进入相应的 `modules/*.py`。

### 5.2 `backend/db.py`：SQLite 组合根

- 定义当前 `SCHEMA_VERSION = 20` 和 S10 基线后的顺序迁移。
- 创建基础表、索引、不可变触发器、默认 CCD/色散数据、帮助主题和模板。
- 开启外键、WAL 和 `busy_timeout`。
- 通过进程内写锁串行化写事务；异常时回滚。
- 为测试构建的示例扩展应用隔离迁移。

表结构目前集中在此文件。修改数据模型时先确认表所有者，新增版本化迁移和升级测试，不要直接改写已经发布的迁移含义。

### 5.3 `frontend/src/App.tsx` 与 `layout/WorkspaceApp.tsx`：前端装配

- App.tsx 管理登录与首次管理员状态；layout/WorkspaceApp.tsx 管理全局设置、健康状态、运行消息、当前方法、通知和导航目标。
- 页面定义在 pages/ 各业务目录，WorkspaceApp 只通过原有 props 和回调分派页面。
- 把采集、色散、分析、后处理、报告、维护等较大的功能交给独立页面组件。

当前没有使用独立路由库；`WorkspaceApp` 的 `target` 状态和模块导航键共同决定活动页面及内部视图。修改导航时要同时检查 `manifest.py`、`navigation.ts` 和 `App.tsx` 的页面分派。

## 9. 关键业务链路

### 9.1 方法到报告

```text
方法草稿 → 条件/谱线校验 → 发布不可变方法版本 → 设为当前方法
  → 样品队列 → 设备/色散准备 → 采集任务与原始帧
  → 定量分析输入快照 → 重复质控快照 → 标准曲线快照
  → 样品结果合并 → 版本化报告模型 → 预览确认 → 导出/打印
```

阅读时重点关注版本 ID 和哈希如何沿链路传递。采集、分析、曲线和报告不能只引用“当前最新配置”，必须能回到执行时的确切版本或快照。

### 9.2 旧数据迁移

```text
原始文件（只读）
  → 记录路径/大小/时间/SHA-256
  → staging 解析与结构校验
  → 生成诊断、映射、警告和拒绝项
  → 单事务提交
  → 以源哈希保证重复导入幂等
```

`.MTD/CFG/OPT`、`.sam`、`.cdt/.cmt/.edt/.wdt`、`.pdt/.dat` 由不同步骤和服务处理。不要为了“兼容”而回写旧 Access 文件，也不要修改历史样本来让测试通过。

### 9.3 模拟设备与真实设备

- `modules/devices.py` 定义适配器契约和 ACQ 回放模拟器。
- `modules/acquisition.py` 在保留源传输哈希的同时，用稳定种子派生可重放的燃烧帧、暗帧、重复和样品差异。
- `modules/hardware_acquisition.py` 与 `modules/mercury_calibration.py` 都保留真实串口适配器门禁；缺少正式协议时应返回不可用，不能猜测字节。
- 模拟器用于状态机、UI、算法和故障恢复开发，不替代 S14/S15 的现场证据。

### 9.4 两层本地安全边界

桌面请求同时有两类凭据：

1. Tauri 启动时生成的一次性进程密钥，用于证明请求来自本次桌面进程；HTTP 头为 `X-GeoSpectrum-Process-Key`，WebSocket 使用同名头或查询参数。
2. 登录后得到的 Bearer 会话令牌，用于用户身份和权限。

进程密钥不能替代用户登录，用户令牌也不能绕过桌面进程边界。会话只保存在后端进程内存中，服务重启后全部失效。

## 10. SQLite 与不可变数据

数据库入口是 [`Database`](../app/backend/db.py)；所有连接开启外键和 WAL。写操作通过单一进程锁和短事务完成。

阅读 `db.py` 时建议按以下顺序：

1. 文件顶部的 `SCHEMA_VERSION`、`MIGRATIONS` 和各 `_migrate_vXX`。
2. `Database.initialize()` 中的建表 SQL。
3. `schema_migrations` 的顺序迁移和历史开发标记修复。
4. 默认布局、校准、模板和帮助主题的幂等初始化。
5. 文件尾部的 `read()`、`write()` 事务边界。

许多结果表由 SQLite 触发器禁止更新或删除，例如原始硬件帧、分析曲线结果、合并结果、后处理结果和报告导出。遇到“为什么不直接 UPDATE”时，先查相应不可变触发器和服务中创建新版本/快照的路径。

正式运行数据默认位于 `%LOCALAPPDATA%\cn.geospectrum.desktop`。开发和测试应显式设置 `SPECTRUM_DATA_DIR` 到 `app/.local/runtime/...` 或系统临时目录，不能把数据库、日志和导出样例散放在项目根目录。

## 11. 模块清单、权限、审计与导航

[`modules/manifest.py`](../app/backend/modules/manifest.py) 是四类信息的共同事实入口：

- 模块键、版本、依赖和能力；
- 模块拥有的权限；
- 应记录的审计动作；
- 前端导航条目、内部视图、状态和运行上下文。

`/api/v1/capabilities` 将清单传给前端。`navigationEntries()` 先按用户权限过滤不可见入口，`navigationAvailability()` 再根据当前方法、暂停状态或全时保存模式决定已显示入口是否暂时禁用。这两层不要合并：前者是授权可见性，后者是运行条件反馈，真正的业务权限仍由后端路由检查。

修改模块能力时至少核对：

- 清单键、路由、权限、依赖和导航是否唯一；
- `auth.py` 中内置角色是否应获得新权限；
- 写操作是否在同一事务内记录审计事件；
- `test_architecture.py` 和 API 权限测试是否覆盖；
- 是否需要重新生成 `manifest.generated.json`。

## 12. 测试与验证入口

在 `app/` 目录运行。优先使用 `app/.local/` 或系统临时目录保存缓存和测试运行数据。

```powershell
# 全量后端回归
python -m pytest -p no:cacheprovider --basetemp "$env:TEMP\geospectrum-pytest"

# 前端数值输入单测与生产构建
npm.cmd --prefix frontend test
npm.cmd run frontend:build

# 模块清单与架构契约
python -m pytest -p no:cacheprovider tests/test_architecture.py
python tools/generate_manifest.py

# Tauri/Rust 边界
cargo test --manifest-path src-tauri/Cargo.toml

# sidecar 构建与冻结资源验证
python tools/build_sidecar.py
python tools/verify_sidecar.py
```

按风险选择最小测试集合，不要为了形式重复执行同一规则的多层测试。常用定位方式：

- API、认证、权限：`test_api.py`、`test_auth.py`。
- 数据库升级：`test_schema_migrations.py`、`test_s21_release.py`。
- 某个业务步骤：对应 `test_sXX_*.py`。
- 旧格式：对应迁移测试和黄金样本。
- 前端类型/语法：`frontend:build`。
- 桌面文件、sidecar、loopback：`test_tauri_contract.py`、Rust `cargo test`。

验收结论必须回写到相应步骤报告，而不是只留在终端输出中；只有本次任务确属一个获准验收步骤时才新增或更正验收记录。

## 13. 常见修改的追踪清单

### 新增或修改一个 API 字段

1. `schemas/<module>.py` 的 Pydantic 契约。
2. 对应 `modules/*.py` 服务和数据库读写。
3. `api/<module>.py` 路由边界。
4. `frontend/src/api/index.ts` 类型与调用。
5. 使用该字段的页面。
6. API 契约及领域测试。

### 新增导航入口或内部视图

1. `modules/manifest.py` 的模块导航条目。
2. `validate_manifests()` 允许的页面/视图组合。
3. `frontend/src/navigation.ts` 的 `Page` 和运行条件。
4. `App.tsx` 的页面分派或目标页面的 `initialView/onViewChange`。
5. `manifest.generated.json` 重新生成。
6. 权限、活动高亮、禁用原因和 28 个既有入口回归。

### 修改数据库结构

1. 确定表的模块所有者。
2. 提升 schema 版本并新增有序迁移；不要改写已发布迁移的语义。
3. 明确旧数据转换、失败回滚、幂等和不可变触发器。
4. 覆盖新库初始化和旧库升级两条路径。
5. 需要时更新备份/恢复、发布清单和诊断输出。

### 修改旧格式解析

1. 先按事实来源路径取证。
2. 保留原件、大小、时间和 SHA-256。
3. 在副本或 staging 上解析。
4. 增加黄金样本、拒绝路径和幂等测试。
5. 不生成或回写旧 Access 文件。

### 修改设备控制

1. 业务服务只依赖适配器契约。
2. 模拟器使用固定种子、虚拟时间和输入哈希。
3. 真实命令必须来自正式协议或通信抓取。
4. 覆盖停止、超时、损坏帧、有限重试和安全收尾。
5. 不因模拟测试通过而关闭硬件在环门禁。

### 新增前端文件下载

1. 后端响应提供正确媒体类型和文件名。
2. 前端统一调用 `saveFile()`，不要在页面内直接创建下载链接。
3. 桌面白名单若需扩展，同时修改 Rust 校验和契约测试。
4. 保持浏览器下载回退与 Tauri 取消保存分支。

## 14. 容易误读的约束

- `PLAN.md` 里的目标架构比当前物理目录更理想化；新增代码应向模块边界靠拢，目前 main.py、后端 API/模型和前端请求层已完成拆分，前端页面也已按业务归位；db.py 的迁移脚本留待 R6。
- `manifest.generated.json` 是生成物，`modules/manifest.py` 才是源。
- `deferred_external` 不是失败，也不是通过；它表示软件闭环之外仍缺明确外部输入。
- `legacy_2_0_2` 和 `modern_v1` 是并存的计算档案，不能静默替换旧版复现结果。
- “当前方法”是跨页面运行前置条件；暂停方法时相关入口应可见但禁用，并给出原因。
- `page_scoped` 表示入口本身可达，具体文件或选择条件由页面内部判断。
- 运行事件和审计事件不是同一概念：前者面向状态和操作反馈，后者用于不可编辑的责任追踪。
- 后端生成到指定输出目录的 S18/S19 导出，与前端生成内容经 Tauri“另存为”的 S22 路径是两套明确流程。
- 根目录不是 Git 仓库，不能依赖 `git diff` 发现全部改动；执行任务时应明确记录修改文件和验证命令。

## 15. 注释维护原则

本项目采用“外部 Markdown 解释系统，代码注释解释局部原因”的方式：

- 架构、目录、数据流、阅读顺序、跨模块约束和修改清单优先维护在本文。
- 代码内注释只解释非直观的设计原因、安全边界、兼容口径、不可变约束和算法来源，不逐行翻译代码。
- 公共入口和复杂边界可使用模块注释或 docstring；简单函数名已能表达意图时不增加重复注释。
- 注释必须描述仍然成立的约束，不能把步骤计划或临时状态永久写死在实现中。
- 如果代码变更使本文的入口、链路、门禁或事实来源失效，应在同一任务中更新本文。

开始修改前，再回到 [`AGENTS.md`](../AGENTS.md) 确认当前用户授权、当前步骤和目录边界。
