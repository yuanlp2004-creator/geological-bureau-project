# 新版代码质量审查与整理建议

日期：2026-09-20。性质：研究记录，不是实施授权或验收通过声明。

## 范围和结论

对 `app/backend` 的 125 个 Python 文件进行了语法树、函数体规模、分支和未绑定全局名称扫描；对 `app/frontend/src` 的 86 个 TS/TSX/CSS 文件进行了状态、异步请求、计时器、引用及长行扫描；检查了 1 个 Rust 桌面入口。人工重点追踪采集、硬件采集、汞灯、方法、分析、后处理、报告、数据库、身份、维护、迁移和桌面文件保存中的相关路径，并对照现有测试。扫描覆盖不等于逐行人工审计，本文不保证发现全部问题。

整体有明确模块和测试基础；优先级最高的改动是异常路径、并发边界和导出保护，不是进一步缩减行数。部分文件经过拆分后，跨模块依赖仍然存在；前端还有大量压缩成单行的 JSX 和异步状态处理重复。

上一轮采集完成哈希整理的 3 个改动文件保持原样。本轮没有修改产品源码、测试、计划或历史数据；只新增本研究报告。所有复现使用系统临时目录，退出后清理。本轮未运行全量测试、浏览器端到端、冻结构建或真实硬件验收。

证据分为：**已复现**（实际执行得到结果）、**静态确认**（可直接由源码确认）、**风险待验证**（触发条件需专项实验）。大小估计只描述波及范围，不是工时承诺。

## A. 优先修复具体错误和可靠性风险

### A1. 采集 API 的队列错误处理失效——小，优先

- 位置：`app/backend/api/acquisition.py:43,156`；错误转换函数实际定义在 `app/backend/api/sample_queues.py:22`。
- **已复现**：在临时库启动 TestClient，创建并登录测试管理员，向采集创建接口提交不存在的 `queue_id/queue_item_id=999999`，得到 `NameError: name 'sample_queue_error' is not defined`。默认服务器错误处理会把该分支变成 500，而不是服务原本的业务错误。
- 同文件重命名分支也引用该未定义名称；那一条路径仅静态确认。整个后端的 symtable 名称扫描发现这两处未绑定全局引用，未发现其他同类候选；此扫描不能代替完整静态分析。
- 最小修改：收拢此 API 文件中两类业务错误的转换，保留错误码、状态码、details；检查 step 的队列关联异常也能被正确映射。无需建立全局异常框架。
- 验证：有效队列成功；不存在队列/队列项返回原定 4xx；重命名错误；完成时队列冲突。分别核对 API 和数据库回滚。

### A2. 同一采集任务缺少完整命令互斥——中，优先

- 位置：`app/backend/modules/acquisition.py:606` 的 `step()`，以及同类 start/pause/resume/stop；`app/backend/db.py` 的写锁只保护写事务。
- **已复现**：创建 3 个燃烧帧、无暗帧、预激发为 0 的临时任务；在 `_seeded_acquisition_event` 返回前使用双线程 Barrier，使两次 step 在写事务前拿到同一阶段/帧。一个请求成功返回 burn，另一个得到 `IntegrityError: UNIQUE constraint failed: acquisition_frames...`。
- 这是受控并发交错复现，不是常规单击必现；数据库唯一约束阻止重复帧，但未给用户可控的冲突结果。串行写事务不能保护事务前的状态读取和适配器推进。
- 前端自动推进使用 busyRef，手动操作使用另一组 busy 状态，未形成一个统一的命令入口；具体界面并发仍需浏览器验证。
- 最小修改：先为 S13 单任务命令建立互斥或明确冲突语义，覆盖读取状态、操作适配器、提交及收尾。可参考硬件采集和汞灯已有的每任务锁；不要把多个任务放进一个全局锁。互斥不等于请求幂等，两者分别处理。
- 验证：step/step、step/stop、暂停/继续交错；不同任务互不阻塞；失败后锁释放；已有帧和队列关联不受污染。

### A3. “加后缀”导出存在同名覆盖窗口——中，优先

- 位置：`app/backend/modules/reports.py:247` 的 `_atomic()`；`app/backend/modules/postprocessing/exporting.py:100` 的 `_atomic_write()`。
- **已复现**：两个临时导出同时选择 `same.csv`，在 os.replace 前用 Barrier 对齐，再串行执行实际替换以避免 Windows 文件占用噪声；两套实现均返回 `['same.csv', 'same.csv']`，目录最终只有一个文件。输入内容分别为 first/second，后完成的替换覆盖前一份。最初无替换锁的实验还出现过 WinError 5，不能将所有并发都描述为静默覆盖。
- 原因是先 exists 检查再 replace。原子替换保证单次写入完整，不保证名称分配排他；`error` 策略也有同类检查窗口。
- 最小修改：明确 suffix/error/overwrite 三种语义，先使一个导出入口实现排他名称占用和可靠清理，再让另一个复用。文件保存与业务审计分别归属，不建立万能导出框架。
- 验证：并发同名的 suffix 保留两份内容、error 仅一个成功、overwrite 行为明确；写入失败不损坏旧文件，不残留临时文件。后续考虑外部进程竞争，不能仅靠单个服务实例锁宣称彻底解决。

### A4. 报告缺失输出目录的校验无效——小，优先

- 位置：`app/backend/schemas/reports.py` 的 `ReportExport`；`app/backend/modules/reports.py:275`。
- **已复现输入与判断**：`ReportExport(format='csv')` 接受 output_directory=None；经过 `Path(str(value or ''))` 后得到 `.`，`not str(directory)` 为 False，因此“必须提供输出目录”检查永远挡不住这种输入。
- 未执行实际报告文件导出；沿后续源码可见该路径会被传给文件保存。正常报告页面有空目录判断，但 API 仍允许省略，前端保护不能代替后端契约。
- 最小修改：构造 Path 之前验证非打印导出的原始字符串；明确空串、纯空白、相对路径与目录不可写的处理。保留打印无需输出目录的行为。
- 后处理服务有同样的 Path 后检查，但其 HTTP 模型已拒绝空串/缺字段，不能直接等同于报告 API 的可达问题。
- 验证：缺失/空串/空白拒绝，合法目录成功，打印默认目录行为保持。

### A5. 桌面请求层对写请求也自动重试——小到中，风险优先核实

- 位置：`app/frontend/src/api/client.ts:11`；`app/frontend/src/api/acquisition.ts:133` 起。
- **静态确认**：桌面模式最多尝试 80 次；catch(fetch error) 后继续重发，未按 GET/POST 等方法区分，也无独立的请求截止时间。创建任务和 step 都通过这个入口发 POST。
- **风险待验证**：服务端已完成操作但响应在传输中丢失时，重发可能重复创建或推进。没有在真实桌面环境模拟此网络故障，不宣称已发生重复业务操作。
- 最小修改：分开“等待 sidecar 就绪”和“发送业务命令”；非幂等命令不能凭网络异常盲目重试。明确超时、取消及不确定结果提示；确需重试时增加服务端幂等契约。
- 验证：启动阶段暂时不可达；写入后响应丢失；取消请求不再循环重试；读取请求按约定恢复。

### A6. 旧异步响应可能覆盖当前选择——小到中，一次处理一个页面

- 位置：`app/frontend/src/pages/reports/ReportsPage.tsx:34` 的 selectReport、同页 preview；`pages/methods/SpectralLinesPanel.tsx:41` 的 loadLines；`pages/acquisition/SampleAcquisitionPage.tsx:109` 起的刷新和自动推进。
- **静态确认**：这些请求结束后直接提交状态，未统一判断请求是否仍属于当前选择。快速从 A 切换到 B，A 的较晚响应可能恢复旧详情；自动推进结果也可能覆盖刚切换的任务。实际浏览器触发频率未测。
- 项目已有可复用思路：SpectrumViewerPage 的 detailRequest、LegacySourcePicker 的 requestId，以及采集补充曲线请求的 cancelled 检查。不同页面防护不一致。
- 最小修改：先整理报告详情/预览这一条选择流程，使用请求序号或当前对象校验；再单独处理采集控制。不要把所有页面塞进同一个复杂 hook。
- 验证：受控延迟 A 慢 B 快；切换任务期间旧推进返回；卸载/重新登录；最后显示的内容和选择对象一致。

## B. 值得做的局部结构整理

### B1. 采集完成与状态推进职责——中，先稳定 A2

`acquisition.py` 同时包含模拟点生成、BLOB 编解码、平均计算、SQL、状态推进和审计。step 当前约 125 行；上一轮只是消除哈希重复，未解决这些职责交织。

建议下一次结构整理只取“一个重复采集结束→决定下一个重复或任务完成”这一段，形成清晰的内部流程，保留同一连接和提交点。后续再考虑模拟数据生成。不要一次把整个文件拆成多个相互回调的类。

保留数值黄金值、事件顺序、重复序号、暂停恢复、预热例外、队列关联和错误回滚；先排除并发缺陷，避免重构把缺陷藏起来。

### B2. 后处理页面的选择与表单状态——中，独立收益高

`app/frontend/src/pages/postprocessing/PostProcessingPage.tsx:49` 起有 21 个 useState 调用，覆盖源记录、区间、方法版本、曲线、导出及运行记录。样品采集页面也有大量独立状态。数量是筛选线索，不是应当合并成一个对象的理由。

先取“源记录选择与区间查看”：将选择规则、参数和区间响应放在紧密相关的局部状态中，UI 拆成区间面板；验证筛选、全选/反选和切换记录后的参数有效性。重算和导出留到各自下一轮。避免仅把原页面原封不动搬进一个巨型 hook。

### B3. 长行与未使用旧组件——小，可穿插进行

`ReportsPage.tsx` 只有约 70 行，却包含密集的请求逻辑和大段 JSX；样品采集页面单行最长约 5005 字符。当前行数低不能证明代码精炼。先格式化准备修改的局部函数/组件，避免全仓格式化淹没行为 diff。

`app/frontend/src/pages/spectra/LegacySpectrumViewerPage.tsx` 中的组件未导出；在当前前端源码搜索只出现定义，无消费者，属于删除候选。删除前再检查构建入口和工作区其他引用；不能把名字中含 Legacy 的所有功能都当废代码。

验收以 TypeScript 检查、构建和相关页面冒烟为主，不为纯格式变化新增机械测试。

### B4. 校验大函数按业务规则分组——中，优先级低于实际缺陷

`modules/spectral_lines.py:194` 的 validate_spectral_lines 约 197 行，`modules/methods/validation.py:23` 的 validate_conditions 约 156 行。分支多主要来自真实业务约束，不能简单删条件或改成高度通用的规则引擎。

可按单行数值、谱线关系、布局可达性等稳定职责提取函数；保留错误字段、错误码、累计顺序及多个错误同时返回的行为。仅在下一次需要修改某组规则时整理该组，收益比一次全面改写更明确。

## C. 有收益，但需要单独安排的边界和性能工作

### C1. 分析使用方法模块私有几何能力——中

`modules/analysis/service.py:117` 直接调用 methods._layout、_dispersion、_reference_position。此前 D1–D4 已收拢方法快照，但该几何依赖本来就在剩余清单，不能说此前重构失败或完全没解耦。

最小改动是给一个分析谱线定位流程提供明确的公开几何输入/结果，在原连接下读取，不把 db/私有仓储进一步扩散。验证默认/指定布局、越界谱线、定位修正和分析黄金结果。跨表采集读取另列后续，不顺带全清。

### C2. 列表接口反复加载完整详情——中，先量测

`modules/acquisition.py:330` 逐任务调用 _task_dict；`modules/analysis/service.py:105` 逐运行调用 repository.run；`analysis/repository.py:96` 组装样品、谱线结果、消息、质控和曲线等完整结构。

查询次数及响应体随条目和详情规模增长，列表用途与详情用途没有充分分开。**静态确认结构，未证明现有用户数据下已慢**。不要为消除每一条 SQL 直接改成难读的巨型 JOIN。

先对典型 50 个运行量测 SQL 次数、响应大小和耗时；确有收益后新增摘要能力，选中时请求详情，保留现有调用者兼容。也可以先只在服务内部批量读取，不改变 API。

### C3. 后处理重算编排和跨模块删除——中到大，暂缓

`modules/postprocessing/recalculation.py:63` 的 recalculate 同时编排分析任务、旧结果计算、曲线求值、幂等检查与结果存储；并发重复检测时直接删除本次创建的 analysis_runs。

此处有真实跨模块边界问题，但现有流程明确允许“分析已提交、后处理审计失败则后处理回滚”的部分提交语义，现有测试对此作了断言。先按 sample/result 两种来源拆清编排，再考虑由分析模块公开清理能力；不能借重构改成整体事务或静默删除审计。收益存在，风险高于前述局部工作。

## 建议顺序与不建议修改的范围

1. A1：采集 API 队列错误，一条异常返回流程。
2. A4：报告导出目录校验，一条参数处理流程。
3. A3：先报告同名导出保护，再单独迁移后处理入口。
4. A2：S13 同任务并发控制，先补可重复失败证据再修改。
5. A5、A6：先请求重试，再报告选择响应；采集自动控制单独一轮。
6. B1、B2：采集收尾职责和后处理区间页面，各自单独完成。
7. C1：分析几何公开能力；C2 量测后决定，C3 暂缓。

B3 可在上述相关文件每次修改时局部做；B4 等规则变更时做。以上是建议，不构成一次全部实施的计划承诺。

暂不值得为整洁而修改：历史数据库迁移/建表长文件、已经独立的纯算法、稳定错误类和模块契约小文件、现有只读旧格式解析及浮点兼容规则。数据库事务入口、应用级 Runtime 装配和只读迁移已有清晰机制，应在修复中保留。没有证据支持切换 ORM、全局状态库、微服务或重新搭建架构。

## 验证边界与证据摘要

- 实际执行：全后端 AST/symtable 扫描；前端引用/异步/状态/长行检索；临时 TestClient 无效队列请求；临时库双线程采集推进；两套导出函数的临时目录并发同名写入；ReportExport 与 Path 空目录判断。
- 已复现输出：NameError；采集帧 UNIQUE IntegrityError；两套 suffix 导出各只留下 same.csv；None 目录变为 `.` 且拒绝条件为 False。
- 并发实验通过 Barrier 强制合法线程交错，是证明缺少保护的定向实验，不是性能、概率或真实硬件测量。
- 上轮 10 项定向通过是上轮证据，本轮没有重新执行；历史 188 项全量通过也不是本轮结果。已复现缺陷表明成功主流程测试不能覆盖全部异常和并发路径，但不代表现有测试没有价值。
- 未来只需围绕实际修改补成功路径和最重要失败路径；A1 应增加未定义名称检查，A2/A3 增加受控并发，A5/A6 增加响应丢失/乱序模拟。无需靠扩大覆盖率数字或重复测试替代这些缺口。
