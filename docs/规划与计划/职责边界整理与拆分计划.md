## 1. 复评结论与执行原则

原 29 项候选在上轮曾收窄为 3 项。本轮用户明确把阅读成本也纳入收益，并偏向拆分 1,000 行以上的业务文件，因此重新评估：**19 项纳入修改范围，其中 3 项最小边界修改与 16 项补充拆分均已完成；其余 10 项低收益，默认不改。** 原 B10 仍只纳入报告消费分析结果的子范围，未批准全面跨表清理。

这里的必要性是维护与学习收益，不是功能正常运行的前提。没有因为文件长就认定功能有错，也不承诺拆分提高运行速度。

收益判断：

- **较大**：减少核心版本/结果的跨模块依赖，或让一个很长的业务文件分成能独立理解的流程、算法、适配、视图区域。
- **中等**：明确的规则或呈现职责已有稳定边界，移动后能减少阅读跨度，改动成本可控；不要求必须已有重复实现或已发生故障。
- **较小**：主要是命名、分类、统一形式，或增加对象/转发的成本高于目前收益。本轮不改。

超过 1,000 行的业务文件列为优先拆分对象。数据库基线、历史迁移和静态声明不机械适用此规则。目标是主文件回到容易阅读的体量；尽量低于 1,000 行，但不为凑行数打散状态机，也不靠删除空行或压缩代码达标。若某个完整控制流程仍较长，应解释保留原因。

保留模块化单体、现有 API、事务、数值、安全状态和 UI 行为。拆分优先搬移已有代码，不引入通用框架、统一四层目录或全局状态库。

默认不改的项目不作为其他阶段的隐含前置依赖。本轮选定范围已全部实施；实际归属与验证记录见第 7 节。

## 2. 已完成的 3 项最小边界修改

### M1：谱线编辑与方法版本的公开边界（原 B06，优先级 1）

- 证据：[spectral_lines.py](../../app/backend/modules/spectral_lines.py) 的 `_payload/_commit` 调用方法服务 `_latest_row/_insert_payload_draft/_valid_actor/_method_dict`，并直接更新 `methods`、读取 `method_runtime_state`。[methods/service.py](../../app/backend/modules/methods/service.py) 又调用谱线规则。
- 为什么值得：谱线编辑实际生成方法版本，版本事务是核心一致性边界。目前调用方必须知道方法内部如何读最新版本、创建草稿、更新时间及装配返回值；方法版本实现变化会连带影响谱线编辑。
- 最小范围：为这条编辑链提供方法模块拥有的公开事务能力，把现有逻辑原样收拢；谱线服务继续负责谱线操作意图、现有校验和谱线审计语义。读取几何/快照优先复用现有公开入口。
- 不包含：完整拆分 `spectral_lines.py`、重构全部方法仓储、统一所有序列化、把全部规则改为纯函数。仅当保持依赖方向确实需要时才移动小段共享规则，不预建包。
- 保持：同一个外层事务、原校验顺序、草稿版本、当前版本、审计、返回结构和错误契约。只给私有函数改名或再加一层转发不算解决边界。
- 验证：原方法/谱线成功编辑和非法输入；失败整笔回滚；新版本及旧版本不可变；API 返回等价。优先复用 `test_methods.py`、`test_spectral_lines.py`、`test_method_snapshot_boundary.py` 的相关项。

### M2：报告读取分析结果的公开边界（原 B10 的一个子范围，优先级 2）

- 证据：[reports.py](../../app/backend/modules/reports.py) 的 `_build_model` 直接查询分析运行、样品、质控、合并结果、活动曲线及曲线快照，还联接方法表。
- 为什么值得：报告需要的是明确版本的分析结果，目前必须了解多个分析内部表及其一致性关系。把读取归还所有者，可以让分析内部变化不直接扩散到报告，并明确谁提供结果事实。
- 最小范围：分析模块提供“报告所需结果快照”的公开读取能力，绑定报告现有读取事务；方法身份使用现有方法快照能力。只迁移原有查询与数据还原，不改变查询顺序、数量量级或快照时点。报告仍决定报告准入、筛选、显示格式和排版。
- 不包含：所有模块跨表访问一次性清理、整个报告服务拆包、渲染器分离、分析服务整体拆分、抽象通用快照框架。
- 保持：完成状态、质控与活动曲线/合并结果对应检查、具体版本、错误优先级和输出内容。接口不暴露 SQLite 行或允许任意 SQL，也不把查询移到新文件后仍由报告访问私有方法。
- 验证：合格分析生成报告；未完成、未质控/不可发布、缺合并结果或曲线不匹配时维持原拒绝；固定输入下报告模型、HTML及导出一致。复用 `test_s19_reports.py` 及必要 S17 样本。

### M3：设置表单自己负责输入校验（原 F01，优先级 3）

- 证据：[WorkspaceApp.tsx](../../app/frontend/src/layout/WorkspaceApp.tsx) 的 `saveSettings` 使用 `.settings-page [data-numeric-input]:invalid` 查子页面 DOM。[SettingsPage.tsx](../../app/frontend/src/pages/settings/SettingsPage.tsx) 实际拥有该表单。
- 为什么值得：工作台依赖设置页 CSS 类名及内部输入结构，局部界面修改可能影响保存前校验。调整小，职责边界明确。
- 最小范围：设置页在自己的保存入口校验，校验通过才调用 `onSave`；工作台保留公共 settings 状态、API 保存和反馈逻辑。
- 不包含：抽取全局 hook、拆整个工作台/设置页、迁移所有公共状态或更改其他页面表单。
- 验证：有效值保存；空值/非法数字不发写请求并定位输入；服务失败保留草稿；重置和主题/密度即时应用不变。前端构建及现有设置页面相关浏览器回归。
